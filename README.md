## 課題 — AIがコードを書き、AIがLGTMする時代の「責任の空白」

生成AIの普及で、コードの大半をAIが書くチームは珍しくなくなりました。次に来たのは「AIがレビューし、AIが承認する」パイプラインです。速い。しかし本番で事故が起きた朝、こう聞かれて答えられるでしょうか。

> **「この変更、考えたのは誰ですか？」**

AIのLGTMは、事故のあとの「なぜ通したのか」に答えられません。承認をAIに寄せるほど、**人間が考えた形跡**が薄れていく——これはツールの精度の問題ではなく、構造の問題です。

## 解 — 承認する権限を持たないAIエージェント

SEKISHOは、CI/CDパイプラインの前に立つ**関所**です。ふつうのAIレビュアーと逆のことをします。

- **AIは絶対に承認しない。** 合格・点数・LGTMという語彙を構造的に持ちません
- 返すのは **反証だけ**。「この行のリトライは二重課金し得る。証拠はこの行」— 全反証にdiff内の実在行への**証拠アンカー**が付きます
- **人間が全反証を裁く**（対応した／リスク受容／反証が誤り＋理由必須）
- 全件が裁かれて初めて **通行手形**（SHA-256ハッシュチェーンの改竄検知つき証跡）が発行され、GitHub Actionsの関が開きます
- AIは**見ていないもの（灰）を正直に申告**します。網羅率100%の演出はしません

「誰が・いつ・何を根拠に通したか」が、監査に耐える形で必ず残ります。

## エージェント構成 — 番人・目付・照合方

単発のLLM呼び出しではなく、権限を分離した多段エージェントです。

```mermaid
flowchart LR
    Z[公開PRのURL] -->|飛脚が自分でdiffを取りに行く| A
    A[diff + デプロイ文脈] --> B[番人 Gemini<br/>反証を生成<br/>証拠アンカー必須]
    B --> C[目付 Gemini<br/>反証を敵対的に検証<br/>diffから導けない反証を自律棄却]
    C --> D[照合方 機械<br/>引用アンカーをdiff本文と突合<br/>捏造を棄却]
    D --> E[人間<br/>全反証を理由つきで裁く]
    E --> F[通行手形 発行<br/>SHA-256ハッシュチェーン<br/>Firestore永続化]
    F --> G[GitHub Actions<br/>手形がなければ403で停止]
```

- **飛脚**（機械）: 公開PRのURLを渡すと、diffを自分で取りに行く（GitHub API・公開リポジトリのみ）
- **番人**（Gemini）: diffを読み、署名者が見落としているかもしれない点への反証を生成
- **目付**（Gemini）: 番人の反証を**敵対的に検証**し、誤読・飛躍・一般論の水増しを自律的に棄却（棄却理由はUIに透明表示）
- **照合方**（機械）: 証拠アンカーの引用がdiff本文に実在するか突合し、ハルシネーションを構造的に排除
- どの段も「承認」を出す権限を持ちません。**Fail open for humans, fail closed for AI approval** — 目付が故障しても反証は人間に届き、AIの承認は決して生まれません

## つくる・まわす・とどける

| コンセプト | 実装 |
|---|---|
| つくる | Gemini API（gemini-2.5-flash）による二段エージェント＋Next.js (App Router) |
| まわす | GitHub Actions ゲート（`action/action.yml`）— 通行手形のないdiffはCIで403停止。**このリポジトリ自身が自分の関所で守られています**（`.github/workflows/gate.yml`・PRを開くと実際にゲートが走ります） |
| とどける | **Cloud Run**（Dockerfile / standalone出力）＋ **Firestore**（手形台帳の永続化・ハッシュチェーン） |

## 使い方（3分デモ）

1. トップページでdiffを貼る（「サンプルdiffを読み込む」で架空の決済サービスの変更を投入可能）
2. 「関所に掛ける」→ 番人・目付・照合方の実行トレースと反証3〜5件が返る
3. 各反証を裁く（3択＋理由必須）→ 全件裁くと「通行手形を発行する」が解錠
4. 手形の記録ハッシュ・チェーンを確認、証跡JSONをダウンロード
5. `/ledger` で台帳全体とチェーン検証、`/api/verify` で改竄検知
6. CIからは `GET /api/gate?diffSha256=<hash>` — 手形がなければ403

APIキー未設定の環境では**サンプル応答モード**で全フローが体験できます（画面に明示されます）。

## 設計原則（破らない5つの規律）

1. **承認しない** — AIの出力に合格・点数・LGTMの語彙は存在しない
2. **網羅を名乗らない** — 「見ていないもの（灰）」を必ず申告する
3. **証拠のない反証は返さない** — 全反証にdiff実在行のアンカー。照合できなければ棄却
4. **判断は人に、記録は鎖に** — 理由のない裁きでは手形は発行されない。手形はハッシュチェーンで改竄検知
5. **AIの権限は反証まで** — エージェントがどれだけ増えても、承認の権限は与えない

## 統制の完全性（なぜ「curlで偽造」できないか）

「AIは承認しない」を名乗る以上、AIやスクリプトが人間を騙って自動承認する経路は塞がねばならない。多層で防いでいる。

1. **反証セッションのHMAC署名** — `/api/refute` が返す反証一式に署名（`lib/attest.ts`）。偽の反証・改変した反証・空の反証を `/api/seal` に送っても署名が合わず403。
2. **レビュアー認証（本番ゲートの最後の関門）** — 手形は誰でも台帳に記録できる（透明性のため拒まない）が、**本番ゲートを開けるのは登録レビュアーが署名した裁きのみ**（`lib/reviewer.ts`）。トークンを持たない裁き（curlでdispositionを注入したもの含む）は台帳に「未認証」と刻まれ、`/api/gate` は403を返す。実運用ではこのトークン照合を企業のSSO/OAuth/mTLSに差し替える。
3. **裁き手の身元をトークンに束ねる** — 手形に記録される裁き手名（`decidedBy`）は、クライアントの自由記入ではなく**認証済みレビュアー名でサーバーが上書き**する。トークンを持っていても、実在他人（例: 別のエンジニア）名義の承認を詐称できない。台帳は「誰が承認したか」で嘘をつけない。
4. **職務分掌（SoD）** — 変更者（`requestedBy`）と認証済み裁き手が同一なら `selfApproved` を刻み、既定でゲートを拒否。
5. **サーバー刻印** — 裁定時刻はサーバーが打つ（クライアントの自称時刻を信じない）。

> **デモ環境の割り切り（正直な開示）**: このPoCは審査員が「関が開く」体験をできるよう、公開のデモレビュアートークン `demo-reviewer-2026` を1つ開けています。ただしこのトークンで署名した手形の裁き手は必ず **「デモ審査レビュアー（公開デモ用・非実在）」** と刻まれ、実在の人物名にはなりません。**公開文字列で実在レビュアーの承認を偽造することはできない**設計です。本番導入時はこのデモトークンを外し、`SEKISHO_REVIEWER_TOKENS` を企業のSSOに差し替えます（そうすれば公開情報だけで関を開ける経路は消えます）。

### 攻撃と防御（この設計は敵対的レビューで鍛えられました）

開発中、有識者レビューで「`/api/refute` の署名を得たbotが、人間の裁き（`dispositions`）を捏造してcurlで自動承認できる」穴が見つかりました。「AIは承認しない」を名乗る作品にとって看板の反証です。これをレビュアー認証で塞いだ後の実挙動:

```bash
# 攻撃: 反証の署名を得て、automation-bot 名義の裁きを注入（レビュアートークンなし）
curl -s .../api/refute -d '{"diff":"...","service":"victim"}'      # → 本物の反証＋署名を取得
curl -s .../api/seal   -d '{...,"dispositions":[{"decidedBy":"automation-bot",...}]}'
#   → 手形は台帳に載る（透明性）。ただし reviewerAttested=false

# その手形で本番ゲートを開けようとすると:
curl -s ".../api/gate?diffSha256=<その手形のhash>"
#   → 403「未認証の裁きです。本番ゲートを開けるのは登録レビュアーが署名した裁きのみ」
```

さらに、公開されているデモトークンを盗んで実在レビュアー名義で承認しようとしても、裁き手名はトークンに束ねられているため詐称は成立しない:

```bash
curl -s .../api/seal -d '{...,"reviewerToken":"demo-reviewer-2026","dispositions":[{"decidedBy":"星野宇潮",...}]}'
#   → 手形の裁き手は「デモ審査レビュアー（公開デモ用・非実在）」と刻まれる（星野宇潮にはならない）
```

台帳（/ledger）にはこの「未認証の裁き」の手形が実際に1件記録されており、`✗ 未認証の裁き（本番ゲート不通過）`と表示されます。**手形は隠さず記録する。しかし関は開けない。** これがこの関所の統制です。

## 名前について

**関所**は、通行手形を検めて人を通した江戸の検問所。手形（証跡）のない者は、どれだけ急いでいても通れませんでした。開発者は公認会計士です。会計監査の世界では「誰が・いつ・何を根拠に判断したか」を残せない記録は証拠になりません。その規律——**AIは結論を書かず、判断と署名は人に残す**——を、デプロイの門に立てたのが本作です。
